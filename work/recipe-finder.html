Case study 12 / Product design

Recipe Finder

An installable, offline-first recipe app with a real meal planner, a shopping list that builds itself, and an ingredient-scaling engine that actually recalculates instead of just relabelling. Built with no accounts, no subscription, and African cuisine treated as a first-class category, not a footnote.

RoleProduct architect & design engineer, solo
StackVanilla JS, service worker, TheMealDB API
Timeline9 weeks, concept to live deployment
StatusView live product ↗
01 / The problem

Most recipe apps fall apart in exactly the environment they're meant to be used in: a kitchen. If the app depends entirely on an external API, it stops working the moment that API has a bad day. If there's no offline support, a saved recipe becomes unreachable the second the WiFi drops, which in a kitchen is often. And most of them fragment the actual job into separate tools, so searching, saving, planning the week, and building a shopping list happen in three or four different apps that don't talk to each other.

Beyond the technical fragility, most platforms treat African cuisine as an afterthought, if it appears at all, despite it being a primary cuisine for a large and actively searching diaspora audience.

Layer onto that the usual pile of ads, forced account creation, and heavy JavaScript bundles that load slowly on a phone standing next to a stove, and the result is that people spend more time fighting the app than actually cooking.

02 / The thinking

The vision was a recipe platform that behaves like a native app, instant, offline, no barriers, so people focus on cooking instead of clicking. That meant four things were non-negotiable from the start: the app has to work with zero connectivity, it has to respect privacy with no accounts or tracking, every interaction has to feel instant rather than "loading," and the workflow has to be complete, discovery through planning through shopping, in one place rather than stitched across apps.

I rejected leaning on a single external API as the sole data source, since that makes an outage someone else's problem that becomes your outage. Instead I built a dual-source model: a local curated recipe database provides baseline functionality that works with zero network at all, and a live TheMealDB integration enriches results when the connection is available. Both get normalized into one unified format, so search and filtering behave identically regardless of where a result actually came from.

I also rejected the standard search-by-ingredient-only entry point. Regional discovery got built in as a first-class option, African cuisine sits alongside Italian and Chinese as its own explorable category, not buried under an "Other" tab, because that's a real, underserved search intent I could see myself and see reflected in how people actually search for Jollof or Egusi online.

Feature depth, not feature count

Ingredient scaling engine

Real math, not display tricks: units are preserved and converted (2 cups becomes 4 cups, not "2 cups x2"), nutrition estimates and cook time recalculate with it.

Meal planning

A full seven-day grid with breakfast, lunch, and dinner slots, and a shopping list generated from the whole week in one click.

Shopping list

Aggregates ingredients across recipes, tracks which recipe each item came from, and shares via the Web Share API with a clipboard fallback.

Voice search

Native Web Speech API integration with a visible listening state, and a graceful fallback to text input where speech isn't supported.

Regional discovery

30+ cuisine filters and 12 regional exploration cards, plus quick modes for Random, Quick Meals under 30 minutes, and Healthy.

Recipe detail drawer

Hero image, a persistent ingredient checklist, a real-time serving scaler from 0.5x to 5x, and a YouTube walkthrough embed where available.

03 / The business and the users

Built for home cooks planning a week of meals, not just looking up a single dish, which is why the meal planner and shopping list exist as core features rather than an add-on. It's also built for the privacy-conscious user who is tired of subscription fatigue and cloud dependency for something as simple as a recipe box: there are no accounts, no tracking, and no background data transmission, and every piece of state (saved recipes, the shopping list, the weekly plan, UI preferences) lives in structured localStorage on the user's own device.

That's also the business thesis. Instead of chasing recurring subscription revenue, the value proposition is that people keep what they create, with no vendor lock-in, positioned against cloud-dependent competitors that need a monthly fee to keep working.

04 / The constraints

Shipped as an installable Progressive Web App with a full service worker strategy: pre-cached core assets for instant loads, network-first fetching with a cache fallback so a weak connection degrades gracefully instead of breaking, offline image placeholders so nothing shows a broken icon, and versioned cache cleanup so updates don't leave stale assets behind. Built entirely in vanilla JavaScript with a centralized AppState class rather than a framework, which kept the bundle light enough to install and run well on modest devices, exactly the devices most likely to be in an actual kitchen.

The honest limitations are documented rather than hidden: the image-based visual search exists in the UI but the backend analysis isn't implemented yet, and the "Trending" section currently uses randomized selection rather than real popularity data. Both are flagged as a known state, not disguised as finished features.

05 / The outcome

Live and installable, meeting full PWA installability standards with 90+ Lighthouse scores across performance, accessibility, and PWA criteria. The most useful feedback I got from an early user was simply: "I forgot this was a website." That's the bar a PWA is trying to clear, and it's the reason I still think the format is one of the more underused distribution channels available to an independent builder: no app store approval, no platform revenue share, just a URL and a good service worker.
